# 12. Installation runs at first launch, from a package that needs no engine

Date: 2026-08-26 · Status: Accepted · Source: [#86](https://github.com/okqixiaobao727-design/GPT-VoiceCoding/issues/86)

v1.0 has to place two artifacts in files the user owns: ADR 0011's fingerprinted hook block in `<config dir>/settings.json`, and the login `LaunchAgent` that starts Codex's shared app-server daemon ([#82](https://github.com/okqixiaobao727-design/GPT-VoiceCoding/issues/82)). Nothing in this repository owned that. `bridgectl` dials a socket and holds no policy and no state; the menu-bar panel says in its own first line that it is not an editor for installation settings; and a `.app` dragged into `/Applications` has no install step at all — macOS copies a directory and runs nothing. The two installer-shaped modules that did exist rendered ADR 0007's `--plugin-dir` plugin, which ADR 0011 supersedes, and had no caller left once the launcher was parked ([#72](https://github.com/okqixiaobao727-design/GPT-VoiceCoding/issues/72)).

## Decision

**Installation is `gpt_voicecoding.installation` — four modules, and not a seam.** ADR 0001 puts a seam only where something varies, and names two adapters when it does. Here nothing varies: there are two artifacts, not two implementations of one interface, and no wire between the parts. So there is no vocabulary to share and no protocol to declare. `__init__.py` holds the one small result type every item answers with, the one write they all go through, and the recorded intent; one module per artifact holds one mechanism each; `__main__.py` names the items explicitly, the way the composition root names adapters. With two artifacts and no plugin story, a list of two calls **is** the registry, and a third item is a line. Bridge Core is not involved at any point — installation is not policy, and it has to work when no engine is running.

At the time of writing there is one item, `claude_hooks.py`. The Codex login `LaunchAgent` is [#83](https://github.com/okqixiaobao727-design/GPT-VoiceCoding/issues/83)'s to write and it joins those lists there; nothing about the boundary waits on it. It has since been written, as `codex_launch_agent.py`, and the paragraph below is what it added.

**The menu-bar shell runs it at every launch, and it writes only when the machine disagrees with what it should be.** A dragged `.app` has no install step, so first launch *is* the install: the shell spawns the bundled interpreter on `bridge-install reconcile` before it spawns the engine, and reconcile writes nothing when the machine already agrees. It deliberately does not go through the engine: the engine refuses to start without a `config.toml` the user has to write by hand, and an installation that waited for that file would not have happened by the time the user first opens the app.

**The shell is a trigger and nothing more.** The merge, the fingerprint, the render and the reversibility stay in Python, in one place. A second copy of them in Swift is the shape of [#47](https://github.com/okqixiaobao727-design/GPT-VoiceCoding/issues/47), where the control-plane socket path is built independently on both sides with no test holding the two together.

**Uninstall is honoured, so the intent is written down.** Reconcile-at-every-launch and a meaningful uninstall cannot both be true unless something records that the user took the artifacts back. That record is `installation.json`, in the product's own directory rather than in any file the user owns: absent means never installed, and `{"wanted": false}` means uninstalled and reconcile leaves the machine alone. With the intent recorded, restoring a block that has gone missing is honouring what the user asked for rather than overriding them — and it is the only repair there is for the exposure the next paragraph describes.

**A write is atomic, read back, and reported.** Each item renders its whole file, writes it to a temporary path beside the target and `os.replace`s it, then reads it back and compares. Legacy wrote in place (`legacy@1d32845:bridge/hookconfig.py:153-155`); this is adapted rather than copied, because ADR 0011 records concurrent writers of `~/.claude/settings.json` as a real and untested exposure. Atomicity is what keeps a half-written settings file off the disk; it cannot prevent a lost update, where another writer's change between our read and our write is simply gone. So the read-back is the honest part: a mismatch is reported as a failed install naming the file, and never retried into a loop with whoever else is writing.

**Amended by [#83](https://github.com/okqixiaobao727-design/GPT-VoiceCoding/issues/83): the Codex item carries one process action, and it is only ever `bootstrap`.** The principle above is *act, read back, report*, not *write files only* — a plist that launchd has not been told about does nothing until the user next logs out, so an install that only wrote the file would leave the Codex half of a freshly-installed product dead on the day it was installed, which is the one day ADR 0012 exists to cover. So that item writes the plist through the same atomic write and then asks launchd to load the job, and the read-back is `launchctl print` rather than the exit status, because bootstrapping an already-loaded job fails and that failure is the state it was reaching for. **No item ever runs `bootout`, and the asymmetry is the rule: this product starts a daemon the user's Sessions will join, and never stops one they are attached to.** By the time an uninstall runs, the user's own `codex` TUIs are thin clients of that daemon ([#82](https://github.com/okqixiaobao727-design/GPT-VoiceCoding/issues/82)), so an uninstall removes the plist and lets the running daemon live out the login session, and a render that changed while the job is loaded is written but not reloaded — it applies at the next login, and the `Outcome` says so. Which means the file on disk and the job launchd is holding can disagree for one login session, so a status run asks launchd which *program* it is actually running rather than reading our own file back: a job still on the previous render reports `stale` and names what it is running, because the alternative is a report that calls a machine current on the strength of a file nothing has loaded yet. Re-loading a job that died is the *next launch's* reconcile and nothing else, which is an event and not the polling supervisor #83 forbids.

**Amended by [#132](https://github.com/okqixiaobao727-design/GPT-VoiceCoding/issues/132): the program is only the foreign-origin guard; the loaded render's authority is this product's own SHA record plus launchd's GUI-login ASID.** #129 changed resource-limit keys without changing the program, and `launchctl print` exposed the program while exposing no resource-limit field, so program equality called an older loaded definition `current`. When this item explicitly bootstraps a plist, it records the exact file SHA and the job's ASID in `installation.json`, beside and independently of the user's install intent. `status` stays read-only and compares the file on disk with that recorded SHA: equal is `current`; different is `stale` until the next login; missing evidence is an unknown loaded render and fails closed as `stale`. A reconcile first reads the existing file, then renders: when the ASID changes, the existing file's SHA becomes authoritative because it is the file the new login had an opportunity to load. A changed render written later in that same reconcile remains stale. Within one ASID, neither a byte-identical reconcile nor a kickstart is evidence of a reload, so neither replaces the record. The program comparison remains and a foreign program remains stale. Legacy has no loaded-render read-back: `legacy@1d32845:install.sh:174-195` bootstrapped the job and never recorded what launchd loaded, so this behavior is not ported.

**Nothing rolls back.** The two items are independent — a Claude hook block that landed is not made wrong by a LaunchAgent that did not. A run reports per item and exits non-zero if any item failed, and the item that succeeded stays installed.

**The engine publishes its address in a file, so the installed hook can find the engine.** ADR 0011 decided this and it was never built. It is built here because without it the Claude item is theatre: `approval_hook.py` reads the address out of the environment variable the parked launch wrapper set, so a hook installed at user scope exits before it opens a socket on every dialog, and installing it would change the user's settings file in exchange for nothing. The document is the one `bootstrap.py` already defines — the same `socketPath` field — read from a file when no variable is set, which is the fallback order `legacy@1d32845:bridge/hook.py` never needed and #71's probe proved.

## Consequences

**The shell gains one job before it spawns the engine**, and it is a job that can fail without the app being broken: a reconcile that refuses is reported, and the engine still starts. What the user loses in that case is reach into Sessions, which is what the failed item was for.

**The dependency direction is `adapters → installation`, never back.** The Claude adapter's `verify` asks installation what is on disk, because "is our block present and current" is exactly ADR 0003's question about reaching a far side. Installation imports no adapter, no seam and no `core`: the hook's event names and module path are strings, so nothing has to be imported to name them.

**Amended by [#159](https://github.com/okqixiaobao727-design/GPT-VoiceCoding/issues/159): the Claude adapter now makes that read before it dials a Session inbox.** Installation combines its existing on-disk inspection with the recorded install intent into one read-only reach answer. The intent changes the failure's wording, not its verdict: `wanted: false` is still `FAIL` while the loaded adapter is configured to reach Claude Sessions, because the machine and configuration disagree. This behaviour is new rather than ported: legacy had no read-only hook inspection (`legacy@1d32845:bridge/hookconfig.py:143-156`), and its status verb only pinged the daemon (`legacy@1d32845:bridge/__main__.py:205-213`).

**ADR 0007's `hook_plugin.py` and `plugin.py` are deleted** rather than left as dead code. `channel.py` is not touched here; the Relay route that replaced it is [#74](https://github.com/okqixiaobao727-design/GPT-VoiceCoding/issues/74)'s and [#77](https://github.com/okqixiaobao727-design/GPT-VoiceCoding/issues/77)'s to settle.

**The Codex item is a login `LaunchAgent`, which is the shape ADR 0005 moved away from** and which `LoginItem.swift` refuses for the app itself, in those words. The two do not conflict. ADR 0005's reason is the microphone grant, which attaches to whoever owns the process, and the Codex daemon neither wants a microphone nor is ours to own — it is the user's `codex`, started early so the user's own TUIs join a daemon that is already there. The engine remains a direct child of the shell.

**Coverage is one config directory** — the default one. ADR 0011 wrote "installs into each" for a product told about several; v1.0 was scoped to the main account on 2026-08-26 ([#67](https://github.com/okqixiaobao727-design/GPT-VoiceCoding/issues/67)), so the list has one entry and the code takes a directory rather than assuming one.

**Known limitation, left standing knowingly (Simon, 2026-08-26): the round trip is exact only for a file already written the way this renders.** Install read-modify-writes the whole document and renders it at `indent=2` with a trailing newline, so a `settings.json` kept at some other indent, or with its keys in another order, is reformatted by the first install — once, after which it round-trips. And a config directory that had no `settings.json` at all gets one, which uninstall empties rather than removes. No setting is ever lost either way; what is not true is the stronger claim, which ADR 0011 and `CONTEXT.md` both make in the words "byte for byte". Making it true would mean keeping a copy of the user's file in this product's own directory and restoring from it, and that copy is the worse failure: a user who edits `settings.json` while the product is installed would have those edits eaten by the uninstall. The claim is left as written and the gap is recorded here and on [#86](https://github.com/okqixiaobao727-design/GPT-VoiceCoding/issues/86) rather than papered over.

**There is no uninstall in the menu bar**, because the panel is view-only in v1.0. Uninstall is `bridge-install uninstall`, a console script that lands in the bundle's `engine/bin/` beside `bridgectl` by the same pipeline rule that needs no list of script names.

**A test may not reach the machine it is running on, and one line of design was not enough to hold that (#83).** Two drafts of the Codex item loaded a real login job into the author's own launchd — the second started the real shared Codex daemon — because `Launchd` and `home` had defaults that resolved to the real ones and a test that omitted them passed. Defaults were removed and `bridge-install`'s test-only keyword arguments grew to five, but the guard that actually holds is in `tests/conftest.py`: the real `launchctl` runner is taken away from the whole suite, so a test that forgets fails loudly instead of silently changing the machine. Every item added to this boundary that runs a subprocess belongs behind that same fixture.
